Part A

Local development

Your own machine: dev servers with hot reload, seeded demo data, tests.

1

Prerequisites

  • Node.js 20 or newer, with npm (bundled). Check with node -v.
  • PostgreSQL running locally or reachable over the network. A local service, Docker container or managed instance all work. You need a role that can create databases.
  • Git, to clone the repository.
  • Optional: cloudflared, only if you want to share a local demo through a Cloudflare Quick Tunnel (step 10).
No Docker image or hosted service is required. The app is plain Node and PostgreSQL. Prisma, Vite, tsx and the rest come in through npm install.
2

Clone and install

bash
git clone git@github.com:BenzidaneMo/Hajj-Lottery.git
cd Hajj-Lottery
npm install

npm install installs all three workspaces from the repository root, then a postinstall hook builds shared/ to shared/dist. The client and server both import @hajj-lottery/shared, so they won't typecheck or start until that build exists.

If you later edit anything in shared/src, rebuild it with npm run build:shared before the client or server will see the change.
3

Configure .env

The single .env file lives at the repository root, not inside server/. Start from the template:

bash
cp .env.example .env
PowerShell
Copy-Item .env.example .env

Then fill in the values. The server checks them with a Zod schema at startup and exits with the name of any missing or invalid variable. Values are never logged.

VariablePurpose
DATABASE_URLrequiredPostgreSQL connection string for the app and Prisma migrations, e.g. postgresql://postgres:postgres@localhost:5432/hajj_lottery?schema=public
TEST_DATABASE_URLfor testsA separate database for npm test. Its name must contain test, because the suite truncates tables.
NODE_ENVdefault devdevelopment, production or test. Production disables the dev seeds and enables same-origin static serving.
PORTdefault 4000API port.
CLIENT_ORIGINdefault :5173Browser origins allowed to make credentialed API calls, comma-separated. Never *.
SESSION_TTL_HOURSdefault 8Admin session lifetime.
DEV_ADMIN_USERNAME / DEV_ADMIN_PASSWORDdev onlyRead by npm run seed:admin (step 6). Leave them empty and no administrator is created.
TRUSTED_ORIGIN_SUFFIXESopt-inFor example .trycloudflare.com, only when sharing through a Quick Tunnel.
VITE_API_BASE_URLclientAPI origin the dev client calls. Defaults to http://localhost:4000.
Never commit .env. There are no default credentials anywhere in the codebase. Every administrator password comes from you.
4

Create the database schema

Make sure PostgreSQL is running and the database named in DATABASE_URL can be reached. Then apply every committed migration:

bash
npm run prisma:migrate

This runs prisma migrate dev against prisma/schema.prisma. The schema lives at the repository root, not under server/. Prisma creates the database if it doesn't exist yet and generates the Prisma client.

Besides tables, the migrations install raw-SQL constraints: immutability triggers on draw pools and results, the "one open registration year" partial unique index, and CHECK constraints on role/scope shapes. Always create the schema through the migrations. Don't use prisma db push, which skips the raw SQL.

5

Seed reference data

bash
npm run prisma:seed

The seed is idempotent, so it's safe to run again. It loads:

  • Geography: all 69 wilayas and 1,541 communes, with Arabic, French and English names.
  • Development participants: a handful of synthetic identities.
  • A development draw year for the current year, opened for registration, with a commune draw of 10 places in every commune. Without it the registration form would refuse every applicant.

The participants and draw year are skipped when NODE_ENV=production. In production, opening a cycle and allocating places is an administrative act.

Optional: a realistic applicant pool

bash
# one wilaya, quick
npm run seed:mock-applications --workspace server -- --wilaya=27
# nationwide: 1,541 communes × 40 applicants, takes a while
npm run seed:mock-applications

Mock applicants go through the real registration path, so eligibility, weighting and the one-application-per-year rule all apply.

6

Create the first administrator

Development

Set DEV_ADMIN_USERNAME and DEV_ADMIN_PASSWORD in .env, then run:

bash
npm run seed:admin

This creates a SUPER_ADMIN. Running it again resets that account's password. It refuses to run in production.

Production

Pass the credentials as one-off environment variables, never in .env:

bash
ADMIN_USERNAME="…" ADMIN_PASSWORD="…" npm run admin:create
PowerShell
$env:ADMIN_USERNAME = "…"; $env:ADMIN_PASSWORD = "…"
npm run admin:create
Remove-Item Env:ADMIN_USERNAME, Env:ADMIN_PASSWORD

Passwords shorter than 12 characters are refused. If the account already exists in production, the script exits without touching its password, so it can't overwrite a live account.

7

Run in development

The frontend and API run as two processes. Use two terminals:

terminal 1 · API
npm run dev:server   # http://localhost:4000 (tsx watch)
terminal 2 · client
npm run dev:client   # http://localhost:5173 (Vite)

Both reload on file changes. The client calls the API at http://localhost:4000, and the API accepts that origin through CLIENT_ORIGIN.

8

Verify the install

  • localhost:5173 shows the landing page in Arabic, right-to-left. The language switcher flips it to French or English.
  • /register lists wilayas and communes, which means the geography seed worked, and accepts a submission, which means the dev draw year is open.
  • localhost:4000/api/wilayas returns JSON with 69 wilayas.
  • /admin/login accepts the administrator from step 6 and opens the dashboard.
  • npm run prisma:studio opens a browser view of the database, if you want to inspect rows.
9

Run the tests

Server tests (Vitest + supertest) run against a real PostgreSQL database given by TEST_DATABASE_URL. It must be a different database from DATABASE_URL, and its name must contain test. Migrations are applied to it automatically before the suite runs. Client tests use jsdom and need no database.

bash
npm test                                  # every workspace
npm run test --workspace client           # public page tests only, no DB
npm run test --workspace server -- tests/national-id.test.ts -t "normalizes"

Quality checks

bash
npm run lint
npm run typecheck
npm run format:check
10

Production build on this machine

bash
npm run build                          # shared → server → client, in that order
NODE_ENV=production npm run --workspace server start
PowerShell
npm run build
$env:NODE_ENV = "production"
npm run --workspace server start

With NODE_ENV=production, Express also serves client/dist, with an index.html fallback for client-side routes. The whole app then answers from localhost:4000 on one origin, and the production client calls /api/… relative to that origin.

Sharing a local demo

Add TRUSTED_ORIGIN_SUFFIXES=".trycloudflare.com" to .env, start the production server, then run cloudflared tunnel --url http://localhost:4000 in another terminal. This is a demo convenience, not a deployment (for a real one, see Part B). See docs/showcase-tunnel.md for the full walkthrough, and use only synthetic data.

Part B

Production deployment

A real, long-running server reachable at your own domain over HTTPS.

11

Before you deploy

The repository ships no Dockerfile or platform config. It deploys as a plain Node process next to PostgreSQL. This guide uses a Linux VPS (Ubuntu 22.04/24.04) with systemd and a reverse proxy, which is the simplest setup that meets the app's requirements.

Choose a topology

Recommended

One origin

Express serves both the built client and /api on one domain, behind nginx or Caddy. Nothing to configure for CORS or cookies beyond CLIENT_ORIGIN.

Possible

Split frontend / API

Static client on app.example.dz, API on api.example.dz. They must share one registrable domain (same-site). The client's API URL goes in client/.env.production.local.

Demo only

Cloudflare Quick Tunnel

A temporary random URL from your own PC (step 10). Not for real data or real citizens.

Hard requirements

  • HTTPS. In production the session cookie is Secure, so over plain HTTP the admin login succeeds but the browser drops the cookie and you're never signed in.
  • Exactly one proxy hop. The app sets trust proxy to 1 and reads the visitor's IP from the last X-Forwarded-For entry. The login, registration and status-lookup rate limits depend on that IP. Adding a CDN in front of nginx adds a second hop (see step 16).
  • A single app instance. Sessions live in PostgreSQL, but the rate limiters and the batch-operation double-click guard are in memory. Run one process, not a cluster or several replicas.
  • Port 4000 is never public. Only the reverse proxy may reach it. A visitor who could connect directly could forge X-Forwarded-For and get around the rate limits.

Sizing

A small VPS (2 vCPU, 2–4 GB RAM) is plenty for the app itself. The build is the heaviest task it runs. Give PostgreSQL room to grow with the number of applications, and keep backups off the machine.

Prepare the server

Install Node.js, PostgreSQL and Git

bash · Ubuntu
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt-get install -y nodejs postgresql git
node -v   # must be 20 or newer

Create the database and its role

bash
sudo -u postgres psql -c "CREATE ROLE hajj LOGIN PASSWORD 'choose-a-long-random-password';"
sudo -u postgres psql -c "CREATE DATABASE hajj_lottery OWNER hajj;"

Keep PostgreSQL listening on localhost only, which is the Ubuntu default. A managed PostgreSQL service works just as well. Point DATABASE_URL at it and require TLS with sslmode=require.

Create a system user for the app

bash
sudo useradd --system --create-home --home-dir /srv/hajj-lottery --shell /usr/sbin/nologin hajj
13

Fetch, configure and build

Open a shell as the app user. Every command in steps 13 and 14 runs from /srv/hajj-lottery/app:

bash
sudo -u hajj -H bash
cd /srv/hajj-lottery
git clone https://github.com/BenzidaneMo/Hajj-Lottery.git app
cd app
npm ci --include=dev
Keep the dev dependencies. The build (TypeScript, Vite), the Prisma CLI and the admin/seed scripts (tsx) all live in devDependencies. --include=dev makes sure they're installed even if NODE_ENV=production is set in your shell.

Create the production .env

/srv/hajj-lottery/app/.env
NODE_ENV="production"
PORT=4000
DATABASE_URL="postgresql://hajj:choose-a-long-random-password@localhost:5432/hajj_lottery?schema=public"
CLIENT_ORIGIN="https://hajj.example.dz"
SESSION_TTL_HOURS=8
bash
chmod 600 .env
VariableIn production
CLIENT_ORIGINYour public origin, exactly as the browser shows it: scheme and host, no trailing slash. Even on a single origin it's required, because browsers send Origin on every POST and the server rejects unknown ones with 403 FORBIDDEN_ORIGIN.
DEV_ADMIN_*Leave out. The dev seed refuses to run in production anyway.
TRUSTED_ORIGIN_SUFFIXESLeave out. It exists only for the Quick Tunnel demo.
TEST_DATABASE_URLLeave out. Never run the test suite against a production server.
VITE_API_BASE_URLNot needed. client/.env.production already sets it empty so the client calls /api on its own origin. Only a split deployment overrides it, in client/.env.production.local, before building.

Build

bash
npm run build   # shared → server/dist → client/dist
14

Migrate, seed and create the administrator

Apply the migrations

bash
npx prisma migrate deploy --schema prisma/schema.prisma
Use migrate deploy, never npm run prisma:migrate, on a server. The npm script runs migrate dev, which may prompt to reset the database and wipe it. migrate deploy only applies committed migrations, in order, and never generates or resets anything.

Load the geography

bash
NODE_ENV=production npm run prisma:seed

With NODE_ENV=production, the seed loads only the 69 wilayas and 1,541 communes. It skips the synthetic participants and the auto-opened draw year. Set the variable inline as shown, because the seed reads it from the process environment, not from .env.

Create the first SUPER_ADMIN

bash
read -r -p 'Admin username: ' ADMIN_USERNAME
read -r -s -p 'Admin password (12+ chars): ' ADMIN_PASSWORD; echo
ADMIN_USERNAME="$ADMIN_USERNAME" ADMIN_PASSWORD="$ADMIN_PASSWORD" NODE_ENV=production npm run admin:create
unset ADMIN_USERNAME ADMIN_PASSWORD
exit   # leave the app user's shell

Reading the password interactively keeps it out of your shell history. If that username already exists, the script exits without changing anything.

15

Run as a service

A systemd unit starts the app at boot and restarts it if it crashes:

/etc/systemd/system/hajj-lottery.service
[Unit]
Description=Hajj Lottery
After=network.target postgresql.service
Wants=postgresql.service

[Service]
Type=simple
User=hajj
WorkingDirectory=/srv/hajj-lottery/app
Environment=NODE_ENV=production
ExecStart=/usr/bin/node server/dist/index.js
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full

[Install]
WantedBy=multi-user.target
bash
sudo systemctl daemon-reload
sudo systemctl enable --now hajj-lottery
systemctl status hajj-lottery
curl -s http://127.0.0.1:4000/api/health   # {"status":"ok"}
journalctl -u hajj-lottery -f              # live logs

The server loads .env from the repository root relative to its own compiled files, so no EnvironmentFile is needed. If you prefer pm2, run it in fork mode with one instance (pm2 start server/dist/index.js --name hajj-lottery), never -i max.

16

Reverse proxy and HTTPS

Point your domain's DNS A/AAAA record at the server first. Then pick one of the following.

Option 1: nginx + Let's Encrypt

/etc/nginx/sites-available/hajj-lottery
server {
    listen 80;
    listen [::]:80;
    server_name hajj.example.dz;

    # legacy-import uploads are capped at 5 MB by the app
    client_max_body_size 6m;

    location / {
        proxy_pass http://127.0.0.1:4000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        # overwrite, never append: one trusted hop, no client-supplied spoofing
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
bash
sudo apt-get install -y nginx certbot python3-certbot-nginx
sudo ln -s /etc/nginx/sites-available/hajj-lottery /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d hajj.example.dz --redirect   # adds :443, HTTP→HTTPS redirect, auto-renewal

Option 2: Caddy (automatic HTTPS)

/etc/caddy/Caddyfile
hajj.example.dz {
    request_body {
        max_size 6MB
    }
    reverse_proxy 127.0.0.1:4000
}

Caddy gets and renews certificates by itself, and by default it sets X-Forwarded-For from the real client rather than trusting an incoming one.

Firewall

bash
sudo ufw allow OpenSSH
sudo ufw allow 80,443/tcp
sudo ufw enable   # 4000 and 5432 stay closed
Using Cloudflare (orange-cloud proxy) in front of nginx? That adds a second hop, so nginx's $remote_addr is a Cloudflare edge address and the rate limits would group visitors by edge. Turn on nginx's real_ip module with Cloudflare's published IP ranges (set_real_ip_from …; real_ip_header CF-Connecting-IP;), so $remote_addr is the visitor again before it's passed on.
17

Open the first draw year

A production database has geography and one administrator, and nothing else. Registration stays closed until a draw year is open and each commune has a draw configured.

  1. Sign in at https://hajj.example.dz/admin/login and change the bootstrap password.
  2. Create the other administrators (wilaya and commune scopes) under Administrators.
  3. Under Draw years, create the year. Leave it in DRAFT for now.
  4. Configure a commune draw (allocated places) for every participating commune. See below.
  5. Move the draw year to REGISTRATION_OPEN. Only one year can be open at a time.
The console has no "create commune draw" button. It was removed. Commune draws are created through POST /api/admin/commune-draws (SUPER_ADMIN), and the development seed doesn't run in production. Once created, each commune's allocation can be edited in the console.

This script creates one commune draw per active commune through the real API, so each creation is validated and written to the audit log. It's safe to run again: communes that already have a draw are skipped. Run it from any machine with Node 20+:

create-commune-draws.mjs
// APP_URL=https://hajj.example.dz YEAR=2027 SPOTS=10 \
// ADMIN_USERNAME=… ADMIN_PASSWORD=… node create-commune-draws.mjs
const BASE = process.env.APP_URL
const YEAR = Number(process.env.YEAR)
const SPOTS = Number(process.env.SPOTS)
const json = { 'Content-Type': 'application/json', Origin: BASE }

const login = await fetch(`${BASE}/api/auth/login`, {
  method: 'POST',
  headers: json,
  body: JSON.stringify({ username: process.env.ADMIN_USERNAME, password: process.env.ADMIN_PASSWORD }),
})
if (!login.ok) throw new Error(`Login failed (${login.status})`)
const auth = { ...json, Cookie: login.headers.getSetCookie().map((c) => c.split(';')[0]).join('; ') }

const years = await (await fetch(`${BASE}/api/admin/draw-years`, { headers: auth })).json()
const drawYear = years.find((y) => y.year === YEAR)
if (!drawYear) throw new Error(`Create draw year ${YEAR} in the console first`)

const communes = await (await fetch(`${BASE}/api/communes`)).json()
let created = 0
let existing = 0
for (const commune of communes) {
  const res = await fetch(`${BASE}/api/admin/commune-draws`, {
    method: 'POST',
    headers: auth,
    body: JSON.stringify({ drawYearId: drawYear.id, communeId: commune.id, allocatedSpots: SPOTS }),
  })
  if (res.status === 201) created++
  else if (res.status === 409) existing++ // DUPLICATE_COMMUNE_DRAW: already configured
  else throw new Error(`Commune ${commune.code}: ${res.status} ${await res.text()}`)
}
console.log(`Created ${created}, already configured ${existing}`)

SPOTS gives every commune the same allocation. Real allocations differ by commune, so adjust them in the console afterwards. You can only edit an allocation while that commune's draw is still unlocked.

18

Updating a deployment

bash
# back up first (step 19)
sudo -u hajj -H bash -c '
  cd /srv/hajj-lottery/app &&
  git pull --ff-only &&
  npm ci --include=dev &&
  npm run build &&
  npx prisma migrate deploy --schema prisma/schema.prisma'
sudo systemctl restart hajj-lottery
curl -s http://127.0.0.1:4000/api/health
  • Migrations only go forward. Neither the repository nor Prisma has a "down" step, so the backup is the rollback plan.
  • Avoid updating while a draw is running. A restart in the middle of a request rolls back that commune's execution (it stays LOCKED and can be retried), but there's no reason to cause that.
  • Expect a few seconds of downtime during the restart. A single instance has no zero-downtime handover.
19

Backups and restore

The database holds the whole system of record: applications, frozen pools, draw results, the winner archive and the audit trail. Much of it is immutable by design and can't be rebuilt. Back it up daily and keep copies off the server.

bash · one-time setup
sudo mkdir -p /var/backups/hajj-lottery
sudo chown postgres /var/backups/hajj-lottery
/etc/cron.d/hajj-lottery-backup · 02:30 daily, keep 30 days
30 2 * * * postgres pg_dump -Fc hajj_lottery > /var/backups/hajj-lottery/$(date +\%F).dump && find /var/backups/hajj-lottery -name '*.dump' -mtime +30 -delete

Restore

bash
sudo systemctl stop hajj-lottery
sudo -u postgres createdb -O hajj hajj_lottery_restored
sudo -u postgres pg_restore --no-owner --role=hajj -d hajj_lottery_restored /var/backups/hajj-lottery/2027-05-01.dump
# point DATABASE_URL at hajj_lottery_restored (or rename the databases), then:
sudo systemctl start hajj-lottery

Always restore a full dump into an empty database. pg_restore creates the triggers after loading the data, which is what lets the immutability and completeness triggers accept the restored rows. A data-only restore over an existing schema would fire them. Test a restore before you need one.

Go-live checklist

  • The site loads over https://, and http:// redirects to it.
  • .env has NODE_ENV="production", the exact CLIENT_ORIGIN, and no DEV_ADMIN_*, TRUSTED_ORIGIN_SUFFIXES or TEST_DATABASE_URL. The file is chmod 600.
  • From outside the server, ports 4000 and 5432 are unreachable.
  • Admin login works and survives a page refresh, which confirms the Secure cookie over HTTPS.
  • Deep links work after a refresh: /register, /winners, /admin/draws.
  • Repeated wrong passwords on a test account trip the rate limit for that account only, not for everyone. That confirms the real visitor IP reaches the app.
  • A test registration succeeds in one commune, and the status lookup finds it with its receipt reference.
  • The bootstrap admin password has been changed, and the service comes back after a reboot.
  • Last night's backup exists, and a test restore has been done once.
  • The database holds no synthetic data. seed:mock-applications and the reset-* scripts are development tools, and the reset scripts refuse to run in production.
Running on Windows Server instead? The same steps apply. Install Node and PostgreSQL with their Windows installers, use npx prisma migrate deploy, register node server\dist\index.js as a service with NSSM (one instance, working directory set to the repository root), put Caddy or IIS (URL Rewrite + ARR) in front for HTTPS, and close port 4000 in Windows Firewall.

Troubleshooting

Script flags after -- are ignored in PowerShell

Plain npm resolves to npm.ps1, which in some npm/PowerShell combinations drops everything after -- without an error. If a command like npm run reset-participants --workspace server -- --yes ignores its flags, run it with npm.cmd instead. Git Bash and cmd.exe aren't affected.

Cannot find module @hajj-lottery/shared

shared/dist is missing or stale. Run npm run build:shared. npm install normally does this for you through postinstall.

Server exits at startup naming an environment variable

The Zod environment check failed. Make sure .env is at the repository root and the named variable is set. The server never reads server/.env.

Requests fail with a CORS error, or login doesn't stick

CLIENT_ORIGIN must exactly match the origin in the browser's address bar. http://127.0.0.1:5173 and http://localhost:5173 are different origins. The session cookie is SameSite=Lax, so in production the client and API must be same-site.

The registration form refuses every applicant

Registration needs an open draw year and a configured commune draw for the chosen commune. Run npm run prisma:seed in development. If you closed registration while testing, npm run reopen-registration (dev only) reopens it.

Tests refuse to run

TEST_DATABASE_URL is missing, points at the same database as DATABASE_URL, or its database name doesn't contain test. These guards are deliberate, because the suite truncates tables.

"Too many attempts" when signing in

Login is rate-limited to 10 failed attempts per 15 minutes per IP and username. The limiter is in memory, so restarting the dev server clears it.

Production: admin login "succeeds" but you're immediately signed out

The site is being served over plain HTTP. In production the session cookie is Secure, and browsers discard it on HTTP. Serve the site over HTTPS (step 16).

Production: every POST fails with 403 FORBIDDEN_ORIGIN

CLIENT_ORIGIN doesn't exactly match the address bar. Check the scheme (https), the host, www. or not, and that there's no trailing slash. Restart the service after changing .env.

Production: one visitor's failed logins lock out everybody

The app is seeing the proxy's address instead of the visitor's. Make sure exactly one proxy sits in front and it sets X-Forwarded-For. With a CDN in front of nginx, configure real_ip (step 16).

Production: legacy import upload fails with 413

The reverse proxy's body limit is below the app's 5 MB import cap. Raise client_max_body_size (nginx) or request_body max_size (Caddy) to 6 MB.

Production: refreshing /admin/… or /register gives a 404

Express only serves the client and its index.html fallback when NODE_ENV=production and client/dist exists. Check both, then rebuild with npm run build.

Starting a test draw cycle over

These development tools all refuse to run in production:

npm run reset-commune-draws -- --yes undoes every pool freeze and execution and keeps applicants. npm run reset-participants -- --yes wipes every participant, application and result. npm run draft-commune-draws returns READY draws to DRAFT. Without --yes, the reset scripts only do a dry run.
